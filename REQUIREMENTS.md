## 1. Scope

### 1.1 In scope (MVP)

- Organizer accounts. Organizers create, edit, reschedule and cancel the events they own, and delete eligible `SCHEDULED` events (FR-EVT-10).
- Participant registration by email, with email verification. Participants have no accounts.
- Capacity management with a FIFO waiting list and automatic promotion.
- Tickets with unique codes, and online check-in by QR scan or manual code entry.
- Check-in staff role, scoped to a single event.
- Organizer dashboard with real-time check-in count.
- Transactional email notifications with retries and delivery tracking.

### 1.2 Out of scope (MVP)

| Item | Src |
|---|---|
| Participant accounts and passwords | Q1 |
| Platform admin role | Q3 |
| Co-organizers (more than one owner per event) | Q3 |
| Reinstating a cancelled event | Q6 |
| Per-event promotion or registration cutoff (one system-wide 2 h cutoff) | Q2, Q5 |
| Offline check-in and sync — **explicitly excluded from the MVP**. It may be considered later, and the design should not rule it out | Q10, R30 |
| Payments, paid tickets, seat maps, recurring events | A |
| Identity matching at the door, name-based check-in, or any check that the ticket holder is the registrant (tickets are bearer credentials) | R1, R7 |
| Ticket-transfer history or transfer tracking (**possible future enhancement**). Existing check-in and administrative audit records are unaffected | R20 |
| Public event directory or search. Each event is reached through its own public registration link | A |
| Organizer removing or cancelling an individual **confirmed** participant. Removing a **waiting-list** entry is in scope (FR-WL-10) | A, R29 |
| Ticket-code reissue (a new code that invalidates a disclosed one). Future product decision OQ-13 | R22, R31 |
| Multi-language UI and emails | A |

## 2. Glossary and state model

### 2.1 Terms

| Term | Definition |
|---|---|
| **Owner** | The organizer who created the event. Each event has exactly one owner. |
| **Check-in staff** | A person invited by the owner, by email, to check tickets in for one specific event. |
| **Participant** | A person registering with an email address. Has no account. Their **verified normalized email is their only identity**. No name is collected (R1). |
| **Normalized email** | The email address trimmed and lower-cased. Dots and `+tags` are **not** removed (Q8). |
| **Active registration** | A registration in state `PENDING_VERIFICATION`, `CONFIRMED` or `WAITLISTED`. |
| **Start** | The event's scheduled start instant, stored in UTC, with the event's IANA time zone kept alongside it (Q4). |
| **Cutoff** | `Start − 2 h`. System-wide and fixed for the MVP (Q2, Q5, Q9). |
| **Check-in window** | `[Start − 2 h, Start + 12 h]`, system-wide default (Q10). |
| **Schedule version** | A counter on the event, incremented on every date/time change and on cancellation. Scheduled emails are tied to a version (Q4, Q6). |
| **Management link** | A secure, unguessable link that lets **whoever holds it** view and manage one active registration, including cancelling it (Q1, R8). Several management tokens can be valid at the same time, one per issuance (FR-LNK-2). Hiding a link in the UI does not protect a copy that has already been shared. |
| **Share link / Share ticket view** | A separate secure, unguessable, read-only link to a page showing only public event details and ticket-use information (R8, R13, R15). It grants no management rights. |
| **Token issuance** | Generating a new random management or share token, storing only its hash, and delivering the raw value once, in one page or one email (R17). |
| **Link-resolution API** | The read-only request a link page makes to resolve its token (`GET /api/links/<type>`), carrying the token in the `Authorization: Link` header (FR-LNK-10). Its response is the one that FR-LNK-7 makes uniform. |
| **Explicit action** | A deliberate user submission (for example a button press) that is separate from merely opening a link, and is protected against cross-site request forgery. Destructive actions also need a confirmation step (FR-LNK-9, NFR-SEC-8). |
| **Waiting-list removal** | The owner removing one `WAITLISTED` registration from their event (FR-WL-10). The registration becomes `CANCELLED` with reason "removed by organizer". It frees no seat and never triggers promotion. |
| **Token rotation** | A participant replacing **all** currently valid tokens of one type (management **or** share) for a registration with one new token (R19). |
| **Registration cancellation** | Cancellation of **one registration** by the holder of its management link (FR-SELF-2). Followed by a registration-cancellation confirmation email (R16). |
| **Event cancellation** | Cancellation of the **whole event** by its owner (FR-EVT-9, BR-16). Followed by event-cancellation emails. Separate rules from registration cancellation (R16). |
| **Important email** | Ticket confirmation, promotion, reminder, event change, event cancellation. A permanent failure of any of these is shown to the event owner (Q7, R6, R12). |
| **Pending message** | A logical email message in `QUEUED`, `SENDING`, `WAITING_RETRY` or `AWAITING_EVIDENCE` (NFR-REL-13). It may still be handed to the provider. |
| **Settled message** | A logical email message in `ACCEPTED` (accepted by the provider), `FAILED` (definitely not sent, or no attempt could have been accepted), `UNCONFIRMED` (an attempt may have been accepted; outcome unknown, including a message that became obsolete after such an attempt) or `DROPPED` (**definitely not submitted** to the provider, and no longer needed). A settled message is never sent again. A later provider event can still move `UNCONFIRMED` to `ACCEPTED` and add delivery facts (NFR-REL-18). A verified provider event for a `DROPPED` or `FAILED` message is kept as an anomaly without changing that state (NFR-REL-13 g). |
| **Possibly accepted** | A sticky flag on a logical message: set as soon as any attempt of any generation may have been accepted (an ambiguous result or a key-reuse `409`). It is never reset, and it prevents the message from being reported as `FAILED` (NFR-REL-13). |
| **Provider key generation** | The provider idempotency key is the logical idempotency key plus a generation (`…:g1`). Retries within a generation reuse it. A new generation is created only under NFR-REL-16. |
| **Regeneration class** | The class (A, B or C) of a message type, deciding whether a new provider key generation may ever be created (NFR-REL-16, §4.9). |
| **Delivery facts** | Provider-reported facts per generation, derived from the immutable provider-event log: acceptance, delivery, permanent failure, temporary delay, complaint (NFR-REL-18). |
| **Start of sending (claim)** | A message **starts sending** when the transaction that claims it commits with status `SENDING`. The "checks just before sending" in §4.9 (also called the send-time check or freshness check) run **inside** that claim transaction. A message whose claim committed before an event cancellation or reschedule commits may still reach the email provider afterward, within one provider timeout. This is an accepted limit (EC-20, R51). A message not yet claimed when such a change commits fails its check and settles as `DROPPED` if no earlier attempt may have been accepted, and otherwise as `UNCONFIRMED` (obsolete) (NFR-REL-13 e). |
| **Decision time** | The database server time read by a transaction immediately after it acquires its serialization lock: the event lock for event-scoped operations, the account-level locks for account-scoped operations, or the single locked row for outbox-only operations. Time-based business rules (deadlines, cutoffs, windows, expiries and the reminder-slot boundary) are evaluated against the decision time, and it is recorded wherever a requirement refers to when something happened. It is a **business-rule time, not the commit timestamp**: it comes before the commit by the transaction's remaining duration, which is bounded by a transaction time limit (NFR-TIME-2). If two operations on the same event are serialized by the event lock (at least one of them takes it exclusively), their decision times are in commit order. Operations that both take only the shared event lock run concurrently, and their decision-time order may differ from their commit order; no requirement depends on that order. |
| **Required notice** | A registration-cancellation confirmation (FR-NTF-10) or a waiting-list removal notice (FR-NTF-14). Required notices are never dropped by event cancellation (BR-23) or deletion (FR-EVT-10). |
| **Deletion marker** | The minimal record kept after an event is deleted so its audit records stay interpretable (FR-EVT-14). |
| **Sign-in request** | A request for an organizer sign-in link for one normalized email address. At most one is active per address. It expires 15 minutes after its decision time, and its first confirmation uses it up (FR-ORG-3, R55). |
| **Session** | A server-side record of a signed-in organizer (**organizer session**, FR-ORG-4) or of an accepted staff invitation on one device (**staff session**, FR-STAFF-2). Identified by a random ID held in a cookie and stored only as a hash (R55). |
| **Reminder slot** | The single reminder allowed per (registration, schedule version). It is filled by exactly one logical message: a scheduled reminder, or a ticket, promotion or event-change email that counts as the reminder (FR-NTF-2, FR-NTF-3). |

### 2.2 Registration states

```
                    verify (before cutoff, seat free)
PENDING_VERIFICATION ───────────────────────────────► CONFIRMED ──► CANCELLED
        │      │      verify (before cutoff, full)        ▲   (participant before Start and
        │      └──────────────────────────────► WAITLISTED│    not checked in, or event cancelled)
        │                                          │   └──┘ promotion (FIFO, before cutoff)
        │                                          └──────► CANCELLED (participant or event cancelled)
        └──► EXPIRED (link expired, cutoff reached, or event cancelled before verifying)
```

- `CANCELLED` and `EXPIRED` are terminal. Records are kept as history (Q8).
- A `CONFIRMED` registration has exactly one ticket. A ticket is either *not checked in* or *checked in*. A ticket is invalid if its registration is `CANCELLED` or its event is cancelled.
- When a registration becomes `CANCELLED` or `EXPIRED`, its management and share tokens stop granting any action (FR-LNK-6).
- After the cutoff, `WAITLISTED` entries stay `WAITLISTED` but frozen. If the event is moved later, they become eligible again with their positions kept (Q9).

### 2.3 Event states

- **Stored states:** `SCHEDULED` → `CANCELLED` (terminal, Q6). Only an eligible `SCHEDULED` event can be deleted (FR-EVT-10). A `CANCELLED` event is **never deleted** in the MVP. It stays stored and visible to its owner (R39).
- **Time-based phases of a `SCHEDULED` event:** *registration open* (`now < Cutoff`), *registration closed* (`Cutoff ≤ now < Start`), *started* (`now ≥ Start`).

- Participant rights belong to **whoever holds the management link**, not to a verified person. Holding the share link gives no management rights. (R8)

- Every authorization check is done on the server, per request, against the specific event ID. An organizer who changes an event ID in a URL must get `404`/`403`, never another organizer's data. (A)
- Check-in staff must never see the participant list or participant email addresses. Scan results show the **outcome only** (§4.6). (Q3)
- Revoking staff access takes effect on that staff member's very next request. (A)

## 4. Functional requirements

### 4.1 Organizer accounts

| ID | Requirement | Src |
|---|---|---|
| FR-ORG-1 | Organizers sign up and sign in with an **email sign-in link** (FR-ORG-3). An account is created only when a sign-in is first confirmed, so its email is verified before any event can be created. | Q3, R55 |
| FR-ORG-2 | Organizer authentication is **passwordless**, using single-use email sign-in links and server-side sessions stored in PostgreSQL (FR-ORG-3 to FR-ORG-8). The MVP uses no passwords and no external identity providers. **MFA is not required in the MVP.** The design must allow adding a second factor (for example passkeys) later (OQ-15). | R55 |
| FR-ORG-3 | **Sign-in link.** **(a)** The organizer submits an email address and **always gets the same response**, with similar timing, whether or not an account exists. Creating a sign-in request does the same work in both cases. **(b)** **At most one active sign-in request per normalized email address**, created under the address lock (NFR-CON-7) and backed by a partial unique index. A new request replaces the previous one, whose links then get the generic response. **(c)** The request **expires 15 minutes after its decision time** (Glossary; database clock). It becomes usable only when its transaction commits, so its usable window is slightly shorter than 15 minutes, never longer. Send attempts issue tokens under FR-LNK-1/3, but never extend this expiry. **(d)** Opening a link shows only a confirmation page with the **masked target address**. A session is created only by an explicit confirmation (FR-LNK-9), protected by a pre-session anti-forgery token and an `Origin` check. **(e)** At confirmation, the request must be active and its `expires_at` must be later than the confirmation's decision time. The **first confirmation uses up the request** atomically. Every other token of that request then gets the generic response, as do expired, replaced or unknown tokens (FR-LNK-7). A first confirmation for an address with no account creates the account under the address lock (FR-ORG-1, NFR-CON-7). | R55 |
| FR-ORG-4 | **Sessions.** An opaque random ID of at least 128 bits, in a `__Host-` cookie that is `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`, **stored only as a hash**. Every confirmed sign-in creates a new session. **Idle timeout 7 days**, with "last seen" updated at most every 5 minutes in its own transaction, never inside an event-locked transaction (so idle expiry is accurate to about 5 minutes). **Absolute lifetime 30 days.** Sign-out ends the current session. "Sign out everywhere" ends all of the account's sessions in one account-scoped transaction (NFR-CON-7). **Revocation and expiry apply to every authorization check that runs after they commit.** Event-scoped owner actions re-read the session after the event lock, but a request that already passed that re-check may still complete. Every state-changing request needs an anti-forgery token tied to the session and an `Origin` check (NFR-SEC-8). | R55 |
| FR-ORG-5 | **Re-authentication.** Cancelling or deleting an event, or changing the account email, needs a sign-in confirmed **within the last 15 minutes** (the session's `authenticated_at`). Otherwise a fresh sign-in link is sent to the account's current address. Confirming it creates a new session and revokes the session that requested it. **The link never performs the action.** The owner confirms the action again afterwards. | R55 |
| FR-ORG-6 | **Email change.** Needs FR-ORG-5. At most one active change request per account, enforced by a partial unique index; a new request replaces the old one. A request is always accepted, and a confirmation link (hash-only, issued at send time, **expiring 15 minutes after the request's decision time**, explicit confirmation required, FR-LNK-9) goes to the new address whether or not that address is in use. **Confirmation is one transaction following NFR-CON-7:** take the address locks for the old and new addresses, then lock the account row; check the request is active and unexpired and that the account's email hasn't changed since the request; update the email (the **unique index on account email** is the safety net; a conflict gets the generic "This change can't be completed", which doesn't reveal the other account); revoke the account's other sessions and its active sign-in requests; queue a notice to the old address; write an audit record; mark the request used. A pending change doesn't reserve the new address. Account emails are normalized as in Q8. | R55 |
| FR-ORG-7 | **Recovery.** In the MVP, the sign-in link is the only way into an account. Recovery when access to the mailbox is lost, and self-service account deletion, are **unresolved (OQ-17)**. | R55 |
| FR-ORG-8 | **Authentication audit.** Confirmed sign-ins, bursts of invalid or expired sign-in links, sign-out everywhere, session revocations, and requested, confirmed and failed email changes are audited **by account ID only**, never with email addresses, tokens, session IDs or hashes (NFR-SEC-5, ENG-ERR-6). | R55 |

### 4.2 Event management

| ID | Requirement | Src |
|---|---|---|
| FR-EVT-1 | An organizer can create an event with a **title** (required, ≤ 200 chars), **description** (optional, ≤ 5,000 chars), **local start date and time**, **IANA time zone**, and **capacity** (integer ≥ 1). **Creation is idempotent per organizer:** each request carries a client-generated request ID, unique per organizer and enforced by the database, together with a fingerprint of the normalized request. Repeating a request with the same ID and the same data returns the event already created and creates no further event or scheduled task. Repeating it with the same ID and different data is rejected with a safe conflict and creates nothing. **Limitation:** the uniqueness record belongs to the event, so after an eligible event is deleted (FR-EVT-10) a late retry with the same request ID would create a new event (EC-103). | C, Q4, A (limits), R60 |
| FR-EVT-2 | The start is stored in UTC and the IANA zone is stored with it. All displays and emails show the event's local time with the zone named. | Q4 |
| FR-EVT-3 | A local time that doesn't exist because of a DST transition must be rejected. A local time that is ambiguous because of DST must be resolved by the organizer choosing the offset. | A |
| FR-EVT-4 | The start must be in the future when the event is created or rescheduled. | Q4 |
| FR-EVT-5 | The owner can edit title and description at any time while the event is `SCHEDULED`. These edits trigger no emails. | C, A |
| FR-EVT-6 | The owner can change the date/time while the event is `SCHEDULED` and before Start. The event's time zone never changes: the new local date and time are interpreted in it (FR-EVT-3). Effects are listed in §4.9 and BR-12 to BR-15. | C, Q4, R60 |
| FR-EVT-7 | The owner can increase capacity at any time while `SCHEDULED`. If this happens before the cutoff, FIFO promotion fills the new seats in the same transaction. | Q2, Q5 |
| FR-EVT-8 | The owner can decrease capacity, but never below the current number of `CONFIRMED` registrations. The API must reject such a change with a clear error that includes the **minimum allowed capacity**. | Q5 |
| FR-EVT-9 | The owner can cancel a `SCHEDULED` event before its Start. Cancellation is permanent. Effects are listed in BR-16. Requires recent authentication (FR-ORG-5). | Q6, A (until Start), R55 |
| FR-EVT-10 | The owner can permanently delete an event only if **all** of the following hold, checked in the deletion transaction: **(a)** the event is `SCHEDULED`; a `CANCELLED` event can **never** be deleted in the MVP; **(b)** it has **no `CONFIRMED` and no `WAITLISTED` registrations**; waiting-list entries can first be removed individually (FR-WL-10); **(c)** **no required notice for the event is pending** (glossary). While one is pending, deletion is rejected with "Notifications are still being sent; try again later". A required notice that is **settled**, including one that permanently `FAILED`, expired or ended `UNCONFIRMED`, no longer blocks deletion. Its final status and failure reason are recorded and reported (FR-DSH-6), and listed in the deletion confirmation step before the owner confirms. Deletion never discards or drops a required notice. On deletion, `PENDING_VERIFICATION` and terminal registrations are deleted with the event, their tokens stop working, and any other pending (non-required) messages for the event settle as `DROPPED`, or as `UNCONFIRMED` (obsolete) if an earlier attempt may have been accepted (NFR-REL-13 e). Deletion needs an explicit action with a confirmation step. Requires recent authentication (FR-ORG-5). | Q6, R29, R39, R43, R55, R56, R59 |
| FR-EVT-11 | A cancelled event stays stored and visible to its owner with status **Cancelled**. No delete action is offered for it, and any deletion request is rejected with a clear error ("Cancelled events can't be deleted"). | Q6, R39 |
| FR-EVT-12 | Each event has a public registration page at a URL that can't be guessed or enumerated. | A |
| FR-EVT-13 | Deletion is serialized with all other operations on the event (NFR-CON-1). If a verification, promotion or event cancellation commits first, the deletion is re-evaluated against FR-EVT-10 and rejected if no longer eligible. If the deletion commits first, later requests for the event get a not-found response, and verification links get the generic invalid-link response. | R39, A |
| FR-EVT-14 | **Audit records survive event deletion.** Deletion writes a **deletion marker** that keeps only: the opaque internal event ID, the owner's account ID, the event's scheduled start (UTC) and time zone at deletion, the deletion time and actor, and counts **taken as a snapshot in the deletion transaction**: the number of registrations deleted, and the event's required notices by outcome, each notice counted at most once. `failed_required_notices` counts definite failures: send state `FAILED` without contradicting delivery evidence, or a permanent provider failure fact under NFR-REL-18, including "Delivered, later bounced". `unconfirmed_required_notices` counts notices in send state `UNCONFIRMED`. A notice accepted without a failure fact, or whose delivery evidence contradicts a `FAILED` state (NFR-REL-13 g), is in neither count. Later provider events never change the marker. It does **not** keep the event title or description, participant email addresses, tokens or token hashes. Audit records reference events, registrations and participants only by opaque internal IDs, never by email address (NFR-SEC-5), so they remain interpretable through the marker. It retains no other personal data. Retention periods for markers and audit records are part of OQ-5. | R44, R49, R59 |

### 4.3 Registration and email verification

| ID | Requirement | Src |
|---|---|---|
| FR-REG-1 | A participant registers with an **email address only**. No name or other personal data is collected in the MVP. The verified normalized email is the participant's identity. | C, R1 |
| FR-REG-2 | Submitting the form creates a `PENDING_VERIFICATION` registration and sends a verification link. This **does not reserve a seat**. | Q1 |
| FR-REG-3 | The verification link expires after a configurable period (default **24 h**, A) or at the cutoff, whichever comes first. | Q1, Q9 |
| FR-REG-4 | **Opening** the verification link only shows a confirmation page (event title, local date and time, and a **"Confirm my registration"** button). It changes nothing (FR-LNK-9). When the participant **submits** the confirmation, the system must **atomically** do one of the following, evaluated at the moment of submission: (a) assign a free seat → `CONFIRMED`, issue a ticket; (b) if the event is full → `WAITLISTED` at the end of the queue; (c) if the cutoff has passed, the event is cancelled, or the link has expired → reject with no seat and no waiting-list entry. | Q1, Q9, R27, R28 |
| FR-REG-5 | The result page must immediately show the ticket (code and QR) or the waiting-list position, plus a newly issued management link and, if `CONFIRMED`, a newly issued share link (FR-LNK-2). Email must not be the only way to get this information. | Q7, R17 |
| FR-REG-6 | At most **one active registration per (event, normalized email)**. | Q8 |
| FR-REG-7 | Registering again while `PENDING_VERIFICATION` sends a **fresh** verification link and revokes all previously issued verification tokens for that registration. Tokens issued by send attempts of the new message all stay valid (FR-LNK-3). No second record is created. | Q8, R27 |
| FR-REG-8 | Registering again while `CONFIRMED` or `WAITLISTED` creates nothing. The response must be **identical** to a new registration, and an email gives the owner of the address access to their existing registration. The page must not reveal whether the email is already registered. | Q8 |
| FR-REG-9 | After `CANCELLED` (or `EXPIRED`), the same email can register again as a new registration. It must verify again and gets whatever is available at that moment. | Q8 |
| FR-REG-10 | New registrations are rejected from the cutoff onward and for cancelled events. | Q9, Q6 |
| FR-REG-11 | **Reopening** a used verification link, or submitting it again, shows **"Already confirmed"** only while the link is **within its original expiry** (FR-REG-3) and the registration record still exists. It points to the confirmation email, changes nothing (idempotent), does not show the ticket, does not reveal later registration state (for example a later cancellation), does not issue new links, and does not create another registration. After the original expiry, or if the event was deleted, the generic invalid-link response applies (FR-LNK-7). | R28, R41, R46 |
| FR-REG-12 | Unknown, malformed, expired (FR-REG-3, including expiry at the cutoff), replaced (FR-REG-7) or revoked verification links, and unused links of registrations ended by event cancellation, get the generic invalid-link response (FR-LNK-7). This includes a confirmation **submitted** after its token expired, even if the page was opened while the token was still valid. No special "registration closed" message is shown, so nothing reveals that the token once existed. | R41, R46, R47 |

### 4.4 Waiting list and promotion

| ID | Requirement | Src |
|---|---|---|
| FR-WL-1 | Waiting-list order is FIFO by the moment the participant **verified** (entered `WAITLISTED`), not by when they submitted the form. | C, A (ordering key) |
| FR-WL-2 | When a `CONFIRMED` participant cancels before the cutoff, the first `WAITLISTED` participant is promoted to `CONFIRMED` **in the same transaction**, gets a ticket, and is sent a promotion email. | C, Q2 |
| FR-WL-3 | Promotion is automatic. There is no acceptance step. | Q2 |
| FR-WL-4 | No promotion happens from the cutoff onward. Seats freed after the cutoff stay empty. | Q2, Q9 |
| FR-WL-5 | At the cutoff, each participant still `WAITLISTED` receives **one** email per schedule version saying registration is closed and no place became available. | Q9 |
| FR-WL-6 | A failed promotion email must not release the seat or promote anyone else. | Q7 |
| FR-WL-7 | The secure management page must show a `WAITLISTED` participant's **current** position, calculated at page load. | R5 |
| FR-WL-8 | When verification places a participant on the waiting list, a **waiting-list confirmation email** is sent. **Cancellation rule for this table:** after an event's cancellation commits, every queued message for that event whose claim has **not** yet committed fails its send-time check at claim time and settles as `DROPPED`, or as `UNCONFIRMED` (obsolete) if an earlier attempt may have been accepted (NFR-REL-13 e), **except** event-cancellation emails, and registration-cancellation confirmations and waiting-list removal notices whose transaction **committed before** the event-cancellation transaction (BR-16, BR-23). These can only exist if they committed first, because after an event cancellation commits no registration can be cancelled or removed any more. A message whose claim committed (`SENDING`) before the cancellation committed may still reach the provider afterward (glossary "Start of sending", R51).

## 5. Business rules and invariants

These must hold at all times, including under concurrency and partial failure. Wherever possible they are enforced by database constraints, not only by application code.

| ID | Rule | Src |
|---|---|---|
| BR-1 | `count(CONFIRMED registrations of event) ≤ event.capacity`. | C, Q5 |
| BR-2 | At most one active registration per (event, normalized email). Enforced by a **partial unique index**. | C, Q8 |
| BR-3 | An unverified registration holds no seat and no waiting-list position. | Q1 |
| BR-4 | Promotion is FIFO, automatic, only before the cutoff, and only for a seat that is actually free. | C, Q2 |
| BR-5 | A seat is never left free before the cutoff while someone is `WAITLISTED`. Every seat-freeing operation (cancellation, capacity increase) promotes in the same transaction. | C, Q2, Q5 |
| BR-6 | A registration is promoted at most once, and a single freed seat promotes at most one person. | C |
| BR-7 | A ticket is checked in at most once at any time. A new check-in requires an audited undo first. | C, Q10 |
| BR-8 | Each ticket code is unique. A cancelled registration's ticket is never valid again. Re-registration issues a new code. | C, Q8 |
| BR-9 | No new registrations, verifications, or promotions from the cutoff onward. | Q2, Q9 |
| BR-10 | Participants can cancel until Start. A checked-in ticket can't be cancelled. | Q9 |
| BR-11 | Capacity can't be reduced below the confirmed count. | Q5 |
| BR-12 | Rescheduling keeps every confirmed registration and every waiting-list position. | Q4 |
| BR-13 | Rescheduling increments the schedule version. Cutoff, check-in window and reminder time are recalculated from the new Start. | Q4 |
| BR-14 | Rescheduling to a past time, or after Start, is forbidden. | Q4 |
| BR-15 | Moving an event later can reopen registration and the waiting list. Positions are kept, and no separate "reopened" email is sent. | Q9 |
| BR-16 | Cancelling an event: status → `CANCELLED`; all active registrations → `CANCELLED`/`EXPIRED`; all tickets invalid; registration and promotion stop; one cancellation email per confirmed and waiting participant; management tokens grant no action and share views show "no longer available" (FR-LNK-6, FR-SHR-4); no registration-cancellation confirmations are created for these registrations; **no queued message of any type for the event (reminder, promotion, ticket, ticket resend, waiting-list, change, waiting-list-closed, verification, existing-access, management link replaced, staff invitation) may start sending after the cancellation commits, except event-cancellation emails, and registration-cancellation confirmations and waiting-list removal notices committed before it (BR-23)**. A message **starts sending** when its claim commits with status `SENDING`. A message claimed before the cancellation commits may still reach the provider afterward (EC-20, R51). | Q6, R8, R16, R24, R51 |
| BR-17 | An email that permanently fails never changes seat assignment. | Q7 |
| BR-18 | A state change and its outgoing emails are committed together, or not at all. | C, Q7 |
| BR-19 | Only hashes of management and share tokens are stored. Raw values are never persisted in any table, outbox payload, log or audit record. | R17 |
| BR-20 | Rotation is atomic: old tokens of the rotated type are invalid from the commit onward, a new one is always committed with the revocation, and the other type is never affected. | R17, R19 |
| BR-21 | Viewing a share or management link never changes state. Only an explicit, confirmed action can cancel, rotate or resend. | R15, A |
| BR-22 | Tokens of a `CANCELLED` or `EXPIRED` registration grant no action. Its management tokens get the generic invalid-link response (FR-LNK-6). A new registration for the same email gets new, unrelated tokens. | R16, Q8, R48 |
| BR-23 | **Registration cancellation vs. event cancellation is decided by commit order.** Both are serialized on the same event. If the participant's cancellation commits first, its confirmation is sent, and that registration gets no event-cancellation email. If the event cancellation commits first, the participant's cancellation request gets the generic invalid-link response and changes nothing, no participant-initiated confirmation is created, and the participant gets only the event-cancellation email. The same rule applies to waiting-list removal. | R24, R29 |
| BR-24 | Waiting-list removal never promotes anyone and never changes the relative order of the remaining entries. | R29 |
| BR-25 | A ticket code becomes unusable only through registration cancellation, event cancellation, or its single successful check-in. Link rotation never affects it. | R22 |
| BR-26 | A `CANCELLED` event is never deleted in the MVP. Deletion is possible only for `SCHEDULED` events meeting FR-EVT-10. | Q6, R39 |
| BR-27 | Waiting-list removal applies only to `WAITLISTED` registrations. It never changes a `CONFIRMED` registration, never frees a seat, never promotes, and its notice exists only if the removal committed. | R29, R40 |
| BR-28 | Rotation request IDs are single-use forever. Reusing one never rotates, never revokes, and never issues a token. | R42 |
| BR-29 | Deletion never discards a required notice. It waits while any is pending. A settled required notice, including one that failed permanently or ended `UNCONFIRMED`, no longer blocks deletion once its final state and reason are recorded and reported. | R43, R56 |
| BR-30 | Every invalid-link case, for every link type (including sign-in and email-change links, R55), gets one byte-identical generic response. The only distinct pages are: a used verification link within its original expiry ("Already confirmed", R46), and the share view's ticket-use states (R15). | R46, R47, R48 |

## 6. Main user flows

### F1 — Organizer creates an event
1. The organizer signs in with an emailed sign-in link (FR-ORG-3) and enters title, description, local date/time, time zone and capacity.
2. The system validates the input (future start, valid zone, DST rules, capacity ≥ 1) and stores the start in UTC.
3. The system shows the event dashboard and the public registration link.

### F2 — Participant registers and verifies
1. The participant opens the public link and submits their email address.
2. The system shows the same "Check your email" page whatever the registration state (FR-REG-8).
3. The participant opens the verification link and sees a confirmation page. Opening it changes nothing.
4. The participant clicks "Confirm my registration". In one transaction, the system locks the event, checks the cutoff and status at that moment, and either confirms the participant (issues a ticket, queues the ticket email, and fills the reminder slot with it if Start is less than 24 h away) or waitlists them (assigns the next position and queues the waiting-list confirmation email).
5. The result page shows the ticket or waiting-list position, a newly issued management link and, if confirmed, a newly issued share link.
6. Reopening the verification link later shows "Already confirmed", with no ticket (FR-REG-11). An expired or replaced link gets the generic response (FR-REG-12).

### F3 — Participant cancels, and promotion happens
1. The participant opens the management link and cancels.
2. In one transaction: registration → `CANCELLED` and the ticket is invalid. If the participant was `CONFIRMED` and it's before the cutoff, the first `WAITLISTED` person becomes `CONFIRMED`, gets a ticket, and a promotion email is queued. If Start is less than 24 h away, that email fills the reminder slot. A registration-cancellation confirmation email is queued for the cancelling registration. Its management and share tokens stop granting any action.
3. The dashboard counts update.

### F4 — Check-in at the door
1. Staff (or the owner) scan a QR code or type the code. The client sends the code plus a request ID.
2. The server checks: event, window, ticket validity, check-in state. It sets *checked in* atomically.
3. The client shows the outcome. The checked-in count updates for all connected owner and staff screens.
4. On timeout, the client retries with the same request ID and shows the original result.

### F5 — Owner reschedules
1. The owner changes the date/time (the new Start is in the future, and the event hasn't started).
2. In one transaction: update Start, increment the schedule version, recalculate boundaries, queue change emails to all confirmed and waiting participants, and reschedule pending reminders.
3. Queued emails tied to the old version whose claim has not yet committed are dropped at the claim-time check. An email claimed before the reschedule committed may still reach the provider, rendered from current event data (FR-NTF-8, R51).

### F6 — Owner cancels an event
1. The owner confirms cancellation (the UI warns that it's permanent).
2. In one transaction: status → `CANCELLED`, version incremented, registrations closed, cancellation emails queued.
3. Every other queued message for the event (reminders, promotions, tickets, resends, waiting-list, change, waiting-list-closed, verification, existing-access, management link replaced, staff invitations) that has not yet been claimed fails its claim-time check and is dropped. A message already claimed before the cancellation committed may still reach the provider (R51). The only exceptions are registration-cancellation confirmations and waiting-list removal notices that committed before the event cancellation (BR-23). Share views show "This ticket is no longer available for use", and management links get the generic invalid-link response. No registration-cancellation confirmations are created.

### F7 — Owner manages check-in staff
1. The owner enters a staff email. The system sends an invitation.
2. Staff open the invitation link, see the invitation page, and click "Accept". Only then do they get access, to that event's check-in interface only.
3. The owner can revoke access at any time.

### F8 — Cutoff reached
1. A background job finds events whose cutoff has passed for the current schedule version.
2. It queues one "waiting list closed" email per `WAITLISTED` participant. This is idempotent per version.
3. Pending verification links for the event stop working.

### F9 — Ticket resend
1. The participant opens the management link and asks for a resend.
2. Subject to the rate limit, a new ticket email is queued with its own idempotency key. Its management and share links are issued when it is sent.

### F10 — Participant shares a ticket
1. On the result or management page, or from the share link in a ticket email, the participant copies a share link and sends it to someone.
2. The recipient opens it and sees the event title, local date/time with zone, the QR code and code (while valid), and the transfer statement. Nothing else.
3. At the door the code is scanned and checks in once (FR-CHK-2). The share view then shows "Already checked in".

### F11 — Participant rotates a link
1. On the management page, the participant chooses "Replace management link" or "Replace share link" and confirms after reading the consequences (FR-ROT-2).
2. In one transaction, all valid tokens of that type are revoked and one new token is issued.
3. On success, the new link is shown once, with a copy action. After a management rotation, the page switches to the new management token in memory, without putting it back into the address bar (FR-ROT-5, FR-LNK-10), and a "management link replaced" email is queued to the verified registrant address. On failure, nothing changes, no email is queued, and the old links still work.
4. If the response is lost and the browser retries with the same request ID, the participant sees "already replaced; check your email". There is no second rotation and no second email (FR-ROT-11).

### F12 — Owner removes a waiting-list entry
1. On the participant list, the owner chooses "Remove from waiting list" for a `WAITLISTED` registration and confirms.
2. In one transaction, serialized on the event: if the registration is still `WAITLISTED`, it becomes `CANCELLED` (removed by organizer), the entries behind it move up, an audit record is written, and a removal notice is queued. No promotion happens. If the transaction fails, nothing changes and no notice is queued.
3. If it was promoted or cancelled first, the removal is rejected and nothing changes.

### F13 — Owner deletes an event
1. The delete action is offered only for `SCHEDULED` events. The owner confirms deletion.
2. In one transaction, serialized on the event, the system re-checks FR-EVT-10. If eligible, the event and its pending or terminal registrations are deleted, their tokens stop working, and other queued messages are dropped.
3. If not eligible (cancelled, has confirmed or waiting registrations, or required notices are still pending), nothing changes and the reason is shown.
4. If eligible, the confirmation step lists any required notices that permanently failed, with their reasons, before the owner confirms. After deletion, a deletion marker and all audit records remain (FR-EVT-14).

## 8. Acceptance criteria

The format is *Given / When / Then*. Criteria marked **[concurrency]** must be verified with automated tests that run the operations in parallel against a real database.

### Registration and verification
- **AC-1** — *Given* a submitted registration, *when* it hasn't been verified, *then* it doesn't affect the confirmed count or the waiting-list count.
- **AC-2** — *Given* an event with free seats, *when* a participant verifies before the cutoff, *then* they are `CONFIRMED`, they see their ticket on the result page, and one ticket email is queued.
- **AC-3** — *Given* a full event, *when* a participant verifies before the cutoff, *then* they are `WAITLISTED` at position *n + 1* and see their position.
- **AC-4** **[concurrency]** — *Given* capacity 1 with 0 confirmed and 50 pending registrations, *when* all 50 verify at once, *then* exactly 1 is `CONFIRMED` and 49 are `WAITLISTED` with positions 1–49 and no gaps or duplicates.
- **AC-5** — *Given* an active registration for `bob@x.com`, *when* `BOB@x.com` registers again, *then* no new record is created and the HTTP response is identical to a new registration's.
- **AC-6** — *Given* a pending registration, *when* the form is submitted again, *then* the old link is rejected and the new link works.
- **AC-7** — *Given* a verification link, *when* it is opened after expiry or after the cutoff, *then* no registration becomes `CONFIRMED` or `WAITLISTED`.

### Cancellation and promotion
- **AC-8** — *Given* a full event with a waiting list and a time before the cutoff, *when* a confirmed participant cancels, *then* in the same transaction the waiting-list head becomes `CONFIRMED`, gets a new ticket, and one promotion email is queued.
- **AC-9** **[concurrency]** — *Given* a full event with exactly one waiting participant, *when* two confirmed participants cancel at once, *then* that participant is promoted exactly once and one promotion email exists.
- **AC-10** — *Given* the time is after the cutoff, *when* a confirmed participant cancels, *then* no one is promoted.
- **AC-11** — *Given* a checked-in ticket, *when* its participant tries to cancel, *then* the request is rejected.
- **AC-12** — *Given* a promotion email that permanently bounces, *then* the promoted participant stays `CONFIRMED` and the dashboard flags the failure with its reason.

### Capacity
- **AC-13** — *Given* 80 confirmed, *when* the owner sets capacity to 79, *then* the request is rejected with an error stating the minimum allowed capacity is 80.
- **AC-14** **[concurrency]** — *Given* capacity 10 with 9 confirmed, *when* a verification and a capacity change to 9 run at once, *then* afterwards `confirmed ≤ capacity`.
- **AC-15** — *Given* 3 waiting and a time before the cutoff, *when* capacity is raised by 2, *then* the first 2 by position are promoted.

### Rescheduling and cancellation
- **AC-16** — *Given* a reminder already sent for version 1, *when* the event moves 7 days later, *then* exactly one reminder for version 2 is sent 24 h before the new Start.
- **AC-17** **[concurrency]** — *Given* a queued change email for version 2, *when* the event is rescheduled again (version 3) before that email's claim commits, *then* the version-2 email is never claimed or sent and ends as `DROPPED`. *Given* instead that its claim committed (`SENDING`) before the version-3 reschedule committed, *then* it may still reach the provider (accepted limit, R51). Tests force both orders.
- **AC-18** **[concurrency]** — *Given* queued messages of every type for an event (reminder, promotion, ticket, ticket resend, waiting-list confirmation, change, waiting-list closed, verification, existing access, staff invitation), *when* the event is cancelled, *then* **no claim of any of them commits after the cancellation commits** (they don't start sending, R51). Each one not yet claimed ends as `DROPPED`, and only event-cancellation emails are newly sent. A message whose claim committed before the cancellation may still reach the provider (EC-20). Tests force both orders: claim then cancellation, and cancellation then claim.
- **AC-19** — *Given* a cancelled event, *when* any of its tickets is scanned, *then* the result is `EVENT_CANCELLED`.
- **AC-20** — *Given* an event that has started, *when* the owner tries to reschedule it, *then* the request is rejected.
- **AC-21** — *Given* a `SCHEDULED` event with only pending (unverified) registrations and no pending notices, *when* the owner deletes it and confirms, *then* the deletion succeeds, and the pending registrations' verification links get the generic invalid-link response.

### Check-in
- **AC-22** **[concurrency]** — *Given* a valid ticket, *when* 10 check-in requests with different request IDs arrive at once, *then* exactly 1 returns `CHECKED_IN` and 9 return `ALREADY_CHECKED_IN`.
- **AC-23** — *Given* a processed check-in, *when* the same request ID is retried, *then* the original `CHECKED_IN` result is returned and the checked-in count is unchanged.
- **AC-24** — *Given* the device is offline, *when* a code is scanned, *then* the UI shows "cannot validate" and never shows success.
- **AC-25** — *Given* a successful check-in, *then* every connected owner and staff screen for the event shows the new count within the NFR-PERF-2 target.
- **AC-26** — *Given* check-in staff, *when* they call any participant-list, event-edit or undo endpoint, *then* they get `403`.
- **AC-27** — *Given* a check-in undone by the owner, *then* an audit record exists and the ticket can be checked in again.

### Notifications and reliability
- **AC-28** — *Given* the reminder job runs twice (or on two workers) for the same window, *then* each eligible participant gets one reminder for that version.
- **AC-29** — *Given* the database transaction for a state change rolls back, *then* none of its emails are sent.
- **AC-30** — *Given* the provider returns a temporary error, *then* the message is retried with backoff. *Given* retries are exhausted, *then* the message settles as `FAILED`, or `UNCONFIRMED` if an attempt may have been accepted (NFR-REL-13 d). *Given* a permanent bounce arrives, *then* the bounce fact is recorded (NFR-REL-18). In both cases important emails are flagged on the dashboard.
- **AC-31** — *Given* email status, *then* "accepted by provider" and "delivered" are stored and shown as separate states.
- **AC-32** — *Given* the cutoff passes, *then* each `WAITLISTED` participant gets exactly one "waiting list closed" email for that version.
- **AC-33** — *Given* a full event, *when* a participant verifies before the cutoff, *then* one waiting-list confirmation email is queued containing status `WAITLISTED`, their position, and a working management/cancellation link.
- **AC-34** — *Given* Start is 10 h away, *when* a participant is confirmed or promoted, *then* the reminder slot is claimed in the same transaction by the ticket or promotion email, and the reminder job creates no reminder for that participant and version.
- **AC-35** **[concurrency]** — *Given* a ticket email that occupies the reminder slot, *when* that email is retried, processed by two workers, and the reminder job runs at the same time, *then* exactly one slot record and one logical ticket message exist for that registration and version, and no reminder message exists.
- **AC-36** — *Given* a participant confirmed more than 24 h before Start, *then* their ticket email does not occupy the slot. *When* Start − 24 h is reached, exactly one scheduled reminder is created, even if the ticket email was still being retried or was delivered after Start − 24 h.
- **AC-37** — *Given* the registration form, *then* it asks only for an email address, and no name is stored.
- **AC-38** — *Given* a participant confirmed or promoted at exactly Start − 24 h, *then* the ticket or promotion email occupies the slot for the current schedule version. *Given* one confirmed 1 second earlier (Start − 24 h − 1 s), *then* it does not, and one scheduled reminder is created later.
- **AC-39** — *Given* the ticket email occupied the version-1 slot, *when* the event is rescheduled more than 24 h ahead, *then* the version-2 slot is empty and exactly one scheduled reminder is sent for version 2. *When* instead the new Start is less than 24 h away, *then* the change email occupies the version-2 slot and no scheduled reminder is sent.
- **AC-40** — *Given* a message occupying a reminder slot, *when* the provider returns temporary errors, *then* it is retried as the same logical message (same idempotency key). *When* it fails permanently, *then* it settles as `FAILED` (or `UNCONFIRMED` if an attempt may have been accepted), or a bounce fact is recorded for it; the owner's dashboard shows it with the reason, and no other logical reminder exists for that slot.
- **AC-41** — *Given* a waiting-list confirmation email, *then* it shows the position at message creation and states that the position can change. *Given* the management page, *then* it shows the current position.
- **AC-42** — *Given* a queued waiting-list confirmation email, *when* the participant is promoted or cancels before that email's claim commits, *then* it is dropped and never sent (R51).
- **AC-43** — *Given* the result page, management page, ticket email and promotion email, *then* each shows the statement that the ticket can be transferred but admits one person, once.
- **AC-44** — *Given* a ticket already checked in, *when* the same code is presented by anyone, *then* the result is `ALREADY_CHECKED_IN` and the checked-in count is unchanged.

### Ticket sharing
- **AC-45** — *Given* a valid, not-checked-in ticket, *when* the share link is opened, *then* the page shows the public event title, the local date and time with the IANA zone or an unambiguous label, the QR code, the ticket code and the transfer statement. Neither the HTML, nor any response it loads, contains the participant's email, any management URL or token, cancel/resend/rotate controls, check-in time, or any other registration data.
- **AC-46** — *Given* a share token, *when* it is sent to any management, cancellation, resend or rotation endpoint, *then* the response is the generic invalid-link response and the registration is unchanged.
- **AC-47** — *Given* a ticket forwarded only through the share view, *when* the recipient's code is scanned, *then* it is `CHECKED_IN`. *When* the same code is scanned again by anyone, *then* it is `ALREADY_CHECKED_IN`. The recipient never had any way to cancel the registration.
- **AC-48** — *Given* each email type marked ✔ for "Mgmt link" in §4.9, *then* it contains the forwarding warning (FR-NTF-9). *Given* the ticket, promotion and ticket-resend emails, *then* each also contains a working share link (FR-NTF-11) and the transfer statement (FR-TKT-4).
- **AC-49** — *Given* a shared ticket, *when* the registration or the event is cancelled, *then* the share view shows no QR code or ticket code, only "This ticket is no longer available for use", and no reason or private details.
- **AC-50** — *Given* a share link and a management link for the same registration, *then* their tokens are different and neither can be derived from the other or from the ticket code.
- **AC-51** — *Given* responses from the pages of every link type and from the link API, *then* they include the headers in FR-LNK-8 (`Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `noindex`, and a content security policy allowing scripts only from our origin, with `frame-ancestors 'none'`), and the pages load no third-party resources.

### Rescheduling and failure visibility
- **AC-52** — *Given* a ticket or promotion email queued for version 1, *when* the event is rescheduled to version 2 before the email is sent, *then* the email shows the version-2 local date and time. A waiting-list confirmation email still shows the position as it was at creation, with the warning that it may change.
- **AC-53** — *Given* a reminder that permanently fails (bounce, retries exhausted, or expired at Start) or ends `UNCONFIRMED`, *then* the owner's dashboard lists that participant with the available failure reason, the message's retries all used the same idempotency key, and no second reminder exists for that registration and schedule version.

### Share view states
- **AC-54** — *Given* a checked-in ticket, *when* the share link is opened, *then* it shows "Already checked in" with no QR code, ticket code or check-in time. *When* the owner undoes the check-in, *then* the share view shows the QR code and code again.
- **AC-55** — *Given* a valid ticket, *when* its share link is requested 50 times (including requests with a link-preview or scanner user agent), *then* the ticket is not checked in, the checked-in count is unchanged, and no check-in audit record exists.
- **AC-56** — *Given* a shared ticket, *when* the event is rescheduled, *then* the share view shows the new local date and time.

### Management links in emails and registration cancellation
- **AC-57** — *Given* the verification, waiting-list-closed, event-cancellation, registration-cancellation-confirmation and staff-invitation emails, *then* none contains a management or share token. *Given* any email not marked ✔ for "Share link", *then* it contains no share token.
- **AC-58** — *Given* a participant cancels their own registration, *then* exactly one registration-cancellation confirmation is queued. It confirms the cancellation, says the ticket is no longer valid (or the participant left the waiting list), and contains no management or share link. All earlier management tokens then get the generic invalid-link response and allow no action.
- **AC-59** — *Given* the owner cancels the event, *then* no registration-cancellation confirmation is created for the affected registrations, and each gets exactly one event-cancellation email.
- **AC-60** — *Given* HTTP `GET` and `HEAD` requests, repeated 10 times with browser, link-preview and email-scanner user agents, to the page addresses **and link-resolution API endpoints** of all six link types (verification, staff invitation, management, share, sign-in, email change), *then* no registration is verified, no invitation is accepted, no session is created, no email change is confirmed, nothing is cancelled, rotated, resent or removed, no check-in happens, and no email message is created.

### Token storage, rotation and invalid tokens
- **AC-61** — *Given* management, share, verification, staff-invitation, sign-in and email-change tokens issued on pages and in sent emails, and organizer and staff session IDs, *when* every database table, outbox payload, application log and audit record is searched for the raw token values, *then* none is found. Only hashes are present.
- **AC-62** — *Given* several valid management tokens (result page, ticket email, reminder), *when* the participant confirms a management rotation, *then* every older management token gets the generic invalid-link response on its next use, the new one works, all share tokens still work, a "management link replaced" email is queued, and the ticket code is unchanged.
- **AC-63** — *Given* several valid share tokens, *when* the participant confirms a share rotation, *then* every older share token gets the generic invalid-link response, the new one works, management tokens still work, and the unchanged ticket code still checks in once.
- **AC-64** — *Given* a rotation whose transaction is forced to fail, *then* no token is revoked, the old links still work, and the page shows "Your link was not changed. Your current link still works."
- **AC-65** **[concurrency]** — *Given* two concurrent rotations of the same type, *then* exactly one token of that type is valid afterwards. *Given* a rotation concurrent with a cancellation, *then* the end state is either "rotated, then cancelled" or "cancelled, rotation rejected", and never a partially applied state.
- **AC-66** — *Given* an unknown, a malformed, an expired and a rotated token, *then* all four get byte-identical link-resolution API responses with the same status, and the page renders the same generic view. *Given* 21 failed lookups from one client in 10 minutes, *then* the 21st gets `429` with the same generic body.
- **AC-67** — *Given* a cancelled registration, a cancelled event, or a time after the check-in window, *then* no rotation is offered or accepted. *Given* a `WAITLISTED` registration, *then* only management rotation is offered.
- **AC-68** — *Given* a rotation request without the explicit confirmation step, *then* nothing changes. *Given* more than 5 rotations per hour of one type, *then* the next gets `429` and nothing changes.
- **AC-69** — *Given* a management rotation, *when* a ticket or reminder email queued earlier is sent, *then* it contains a newly issued management link that works, and its outbox record never contained a raw token.
- **AC-70** — *Given* an email with links retried after a temporary error, *then* the links from every attempt work, and only one logical message with one idempotency key exists.

### Round-5 decisions
- **AC-71** **[concurrency]** — *Given* a `CONFIRMED` registration, *when* the participant's cancellation and the owner's event cancellation are submitted at the same time (run at least 100 times), *then* every run ends in exactly one of two outcomes. **(a)** Participant first: registration `CANCELLED` by participant, exactly one registration-cancellation confirmation (sent even though the event is then cancelled), and no event-cancellation email for that registration. **(b)** Event first: the participant's request is rejected, there is no registration-cancellation confirmation, and there is exactly one event-cancellation email. Tests force each order at least once.
- **AC-72** **[concurrency]** — *Given* a management rotation request, *when* it is submitted twice with the same request ID (in parallel, and as a retry after the first committed), *then* exactly one rotation and one "management link replaced" logical message exist. The duplicate gets "already replaced" and its response contains no raw token.
- **AC-73** — *Given* a rotation whose transaction is forced to fail, *then* no "management link replaced" message exists and no token is revoked.

### Engineering standards (R54)
- **AC-136** — *Given* a fake provider that accepts a message and then times out (an ambiguous result), *then* our side always retries with the same provider key, never marks the message failed or delivered because of the timeout, and settles it. The fake simulates three provider behaviors. **(a) Identical replay** of the original acceptance: recorded as `ACCEPTED` with the original provider message ID. **(b) `409 invalid_idempotent_request`** (for example because each attempt issues new link tokens, so the body differs, FR-NTF-12): the message moves to **`AWAITING_EVIDENCE`**, is never `ACCEPTED` without a `200`, a replay or a matched provider event, and is never treated as a permanent failure (NFR-REL-13, R56). **(c)** A duplicate physical delivery is possible **only** through a class B regeneration (NFR-REL-16) or provider misbehavior, and is logged (NFR-REL-3). In every case exactly one logical message exists, and the link tokens from every attempt work.
- **AC-137** — *Given* each error category forced on representative endpoints (including a database-constraint violation and an injected unexpected exception), *then* the status and body follow ENG-ERR-2: a stable code and a correlation ID, with no stack trace, SQL, constraint name, token, hash or secret. Link endpoints return the byte-identical generic response (FR-LNK-7) for every unusable token, including when the failed-lookup counter can't be written. Infrastructure and unexpected failures on link endpoints return a safe `503` or `500` whose body contains only the error code and a correlation ID. That body is identical for every link type and token, and never reveals whether a token, account or registration exists.
- **AC-138** — *Given* an error injected inside one message's or task's processing, *then* it is recorded as a failed attempt, the process keeps running, and other work is unaffected. *Given* an injected unhandled rejection outside every boundary, in the web process and in the worker, *then* each logs a structured error with a correlation ID and exits with a non-zero code. After a restart, leased work is recovered and no committed data is lost. *Given* a message that crashes the worker on every attempt, *then* it settles within the retry limit, as `FAILED`, or as `UNCONFIRMED` if an attempt may have been accepted, so the crash loop ends (AC-183). *Given* a webhook interrupted by a crash before its transaction committed, *then* the provider's re-delivery is applied exactly once.
- **AC-139** — *Given* all logs (including request logs) captured across the full integration and end-to-end suites, and the synthetic sensitive values those suites use (raw tokens, token hashes, test passwords, session IDs, sentinel secrets and test participant emails), *then* none of those values appears in any log record, whether raw, URL-encoded, base64-encoded or JSON-escaped. URLs that contain link tokens appear only with the token redacted. A failure reports only the record position, field name and value type, never the value or the matching log line. Test values are synthetic, never real secrets or addresses. **Limit:** this proves absence only for values the suites exercise. ENG-ERR-6's redaction rules cover the rest.
- **AC-140** — *Given* a branch with a deliberate failure in each required check (format, lint, type-check, unit, integration, build), *then* each pipeline run exits with a non-zero code and merging is blocked. Applies once CI exists (OQ-14).
- **AC-141** — *Given* the supported PostgreSQL version, *then* all migrations apply to an empty database and to the previous release's schema, and running them again does nothing. *Given* an outdated schema, *then* the web and worker processes refuse to start, with a clear error, and apply no migrations.
- **AC-142** — *Given* a fresh clone in a clean CI job, *when* the README steps are followed (setup, environment file from `.env.example`, migrate, start web, start worker, every test command, build), *then* all succeed, and every command in the README exists.
- **AC-143** — *Given* a required environment variable is missing, *then* the process exits with a non-zero code and a message that names the variable without showing any value. *Given* `.env.example`, *then* the secret scan passes.
- **AC-144** — *Given* the codebase, *then* automated import-boundary rules pass: business logic imports neither the HTTP framework nor the database driver; handlers and workers issue no SQL directly; event-scoped data access accepts only a locked transaction (ENG-CQ-2, NFR-CON-4).
- **AC-145** — *Given* the unit and integration suites, *then* they pass in three consecutive nightly runs with randomized test order, without relying on real sleeps for timing (ENG-TST-6).

## 9. Non-functional requirements

### 9.1 Consistency and concurrency
| ID | Requirement | Src |
|---|---|---|
| NFR-CON-1 | Every operation that changes event-scoped state runs in a single database transaction and follows the locking protocol (NFR-CON-4), taking an **exclusive** or a **shared** lock on the event row according to the operation. State-changing operations take the exclusive lock and are therefore serialized per event: their commit order is total, and outcomes such as BR-23 are deterministic. These include registration submission and resubmission, verify, participant cancellation, waiting-list removal, promotion, capacity change, title or description edit, reschedule, event cancellation, deletion, check-in and its undo, ticket resend, share-link issuance, link rotation, and staff invitation, acceptance and revocation. Outbox and scheduled-task claims and insert-only tasks (such as reminder creation) take the shared lock instead (NFR-CON-4 a, e): they are serialized against exclusive operations on the same event, but not against each other. The full list of paths is in AC-133. | C, Q5, R24, R29, R53, R57 |
| NFR-CON-2 | BR-1, BR-2, BR-7 and ticket-code uniqueness are also enforced by database constraints, so they still hold if application code has a bug. | A |
| NFR-CON-3 | Operations have no partial effects. Either everything (state + queued emails + audit) commits, or nothing does. | C |
| NFR-CON-4 | **Locking protocol.** **(a)** Every code path that changes event-scoped state, including background workers and scheduled tasks, runs in one `READ COMMITTED` transaction whose **first statement** locks the event row: `SELECT … FOR UPDATE` for state changes, and `SELECT … FOR SHARE` for outbox and scheduled-task claims and insert-only tasks. **(b)** Any lookup needed to find the event (by token hash, ticket code or public URL) is a plain, non-locking read made **before the transaction begins**. Everything it read is re-checked after the lock is taken. **(c)** **No lock upgrades:** a transaction that may change event-scoped state takes `FOR UPDATE` from the start, and a transaction holding `FOR SHARE` never requests a stronger lock on that event. **(d)** **Lock order:** event rows first (ascending ID if more than one), then any other rows. Inside the event lock, other rows may be locked in any order, because every transaction that could lock them for the same event is either serialized by the same event lock or is an outbox-only path (NFR-CON-6). No path may lock registration, ticket, token, reminder-slot, rotation-request or check-in rows **without first holding the event lock**. **(e)** **Two-phase claim** for outbox messages and scheduled tasks: (1) before the transaction, select candidate (row ID, event ID) pairs without locking; (2) in the transaction, lock those events with `FOR SHARE` in ascending ID order, skipping any event row that no longer exists; (3) lock the candidate rows with `FOR UPDATE SKIP LOCKED`, re-checking that they are still due and unclaimed and belong to a locked event; (4) run the freshness checks, set `SENDING` (or the task's running state), the attempt number and the database-clock lease, then commit. Claims never lock outbox or task rows before the event row. Implementations should claim for one event per transaction to keep shared locks short. **(f)** Within a transaction, statements that lower the confirmed count or raise capacity run **before** statements that raise the confirmed count (NFR-CON-5). **(g)** No external calls inside. **(h)** Row locks serialize operations **only if every applicable code path follows this protocol**. A path that skips it is a defect, even if a constraint happens to catch its effect. Deadlock, serialization and lock-timeout failures are retried a bounded number of times. | R51, R53 |
| NFR-CON-5 | **Confirmed-count safeguard.** `events.confirmed_count` is maintained by **statement-level `AFTER` triggers with transition tables** on `registrations`: one trigger each for `INSERT`, `UPDATE` and `DELETE`, because PostgreSQL allows transition tables only on single-event triggers without column lists. Each trigger computes, per event, the net change: confirmed rows in the new transition table minus confirmed rows in the old one. It first locks the affected event rows in ascending ID order, then applies a relative update (`confirmed_count = confirmed_count + delta`) **only where the net change is non-zero**. This filter lives inside the trigger function, because a statement-level `WHEN` condition can't read row values. `registrations.event_id` is **immutable**, enforced by the database. The events table has `CHECK (confirmed_count >= 0 AND confirmed_count <= capacity)` and `CHECK (capacity >= 1)`. These checks aren't deferrable and statement triggers run at the end of each statement, so the ordering rule in NFR-CON-4 (f) applies **across statements**. These constraints are **additional safeguards** (NFR-CON-2), **not substitutes** for correct transaction design. On their own they don't guarantee FIFO order, promotion or deterministic outcomes. They also can't detect drift from bypassed triggers (disabled triggers, replica session role, `TRUNCATE`), so data changes must never bypass them. An **alert-only reconciliation check** compares `confirmed_count` with the actual number of `CONFIRMED` registrations **in a single statement** (one snapshot). It runs after every concurrency test (AC-134) and periodically in production, and never corrects anything automatically. | R51, R53 |
| NFR-CON-6 | **Outbox-only paths.** Recording a send result, the stuck-send reaper, retry-horizon expiry and webhook processing don't take the event lock. They may lock **only** outbox and scheduled-task rows (and insert delivery-event records), and never lock or modify event, registration, ticket or token rows. Owner-facing failure flags are derived by **reading** outbox status, never written onto registrations. Each such path either locks a single row, or claims rows with `FOR UPDATE SKIP LOCKED` in ascending ID order, so it never waits while holding a lock another transaction needs. Result writes are conditional on the attempt number (NFR-REL-9). Audit records and deletion markers have **no foreign key** to events, so deletion neither waits on them nor removes them (FR-EVT-14). Two further rows may be locked, each **on its own, in its own short transaction**: the send-budget row and the sending-pause state (NFR-REL-14). Webhook processing also appends to the provider-event log (NFR-REL-15). | R53, R56 |
| NFR-CON-7 | **Account-scoped locking protocol.** **(a)** Applies to every transaction that creates or replaces a sign-in request, confirms a sign-in, creates an account, requests or confirms an email change, signs out everywhere or revokes an organizer session. Each runs in one `READ COMMITTED` transaction. Lookups needed to find the account or request are plain reads made before the transaction (as NFR-CON-4 b). **(b)** **Lock order:** (1) transaction-scoped **advisory locks on every normalized email address involved** (for an email change: the old and the new address), in ascending lock-key order (the key is derived from the address under a fixed namespace; a hash collision only adds serialization); (2) the **account row** (`FOR UPDATE`), if the account exists; (3) sign-in request, email-change request and session rows. Sign-out everywhere and session revocation start at level 2. A transaction acquires locks only in this order and never goes back to an earlier level. **(c)** **First-time account creation** happens only under the address lock, with `INSERT … ON CONFLICT DO NOTHING` followed by a read. The unique index on account email is a safety net, not the coordination mechanism. **(d)** If, after taking its locks, a transaction finds that an assumption from its plain read no longer holds (for example an account now exists for the address, or the account's email has changed), it **rolls back and restarts from the beginning**, a bounded number of times (NFR-CON-4 h). Rolling back releases every lock, so a restart can never acquire locks out of order. A unique-index violation is handled the same way, and if it persists it's reported as a generic conflict. **(e)** **No transaction holds both an event lock and an account-level lock** (an address lock or an account row). Event-scoped transactions only read sessions and accounts. **(f)** Account-scoped writers never lock outbox rows; outdated authentication messages are dropped when claimed. Authentication messages have no event and are claimed with `FOR UPDATE SKIP LOCKED` without any event or account lock; the claim then re-checks the request row with `FOR SHARE`. A claim can wait on a request row, but no writer holding a request row ever waits on an outbox row, so they can't deadlock. **(g)** Session "last seen" updates lock only that session row, in their own transaction. **(h)** NFR-CON-4 (c), (g) and (h) also apply. | R55 |

| ID | Requirement | Src |
|---|---|---|
| NFR-REL-1 | **Transactional outbox:** emails are written to an outbox table in the same transaction as the state change, and sent by a background worker. The system never sends email inside a request transaction. | C, Q7 |
| NFR-REL-2 | **Two layers.** (1) **Our send state** (NFR-REL-13): pending `QUEUED`, `SENDING`, `WAITING_RETRY`, `AWAITING_EVIDENCE`; settled `ACCEPTED`, `FAILED`, `UNCONFIRMED`, `DROPPED`. (2) **Provider delivery facts** derived from the immutable provider-event log (NFR-REL-18): delivery, permanent failure, temporary delay, complaint. | NFR-REL-12 | **Priority authentication emails.** **(a)** Sign-in, re-authentication and email-change confirmation messages are **high priority**. Every worker reserves **at least one** concurrency slot that only high-priority messages may use, and high-priority messages also have a dedicated priority budget (NFR-REL-14). Bulk batches are limited in size and in sends in flight. **(b)** Committing a high-priority message issues a `NOTIFY` that wakes workers, with polling as a fallback. Bulk sending is limited by the bulk budget (NFR-REL-14). **(c)** A high-priority message is claimed only if its request is still active and has **at least 2 minutes** of validity left. Retries use short backoff and stop once that is no longer true. The message then settles as `FAILED` (expired), or as `UNCONFIRMED` if an attempt may have been accepted (NFR-REL-13 d); if the request was replaced, it becomes `DROPPED` if `possibly_accepted` is false, and `UNCONFIRMED` (obsolete) otherwise. Authentication messages are class A and are never regenerated (NFR-REL-16). **(d)** **The 2-minute check doesn't guarantee that the provider accepts or delivers the email before the link expires.** Provider queuing, network delays, spam filtering and the recipient's mail system can all delay it. Expiry is enforced **at confirmation** (FR-ORG-3 e, FR-ORG-6): an expired link gets the generic response, and the user can request a new one. **(e)** **Target, not guarantee:** provider acceptance within **1 minute (p95)** of commit under normal operation. Commit-to-acceptance time is measured for every authentication message, and missing the target raises an alert (NFR-OPS-1). Delivery time after acceptance isn't measurable by the system. **(f)** The sign-in page and the README's known limitations (ENG-DOC-1) state that a sign-in email may arrive late or after its link has expired, and that a new link can be requested. | R55, R56 |
| NFR-REL-13 | **Send state machine and provider responses.** **(a) States:** pending `QUEUED`, `SENDING`, `WAITING_RETRY`, `AWAITING_EVIDENCE`; settled `ACCEPTED`, `FAILED`, `UNCONFIRMED`, `DROPPED`. The send state only ever moves toward `ACCEPTED`. **(b) Responses:** a `200` with an ID from any attempt (including a stale worker's), or an identical replay → `ACCEPTED`, recording the provider ID. `409 invalid_idempotent_request` → `AWAITING_EVIDENCE`: no further sends with that provider key, and **never treated as acceptance**. `409 concurrent_idempotent_requests` and `429` → `WAITING_RETRY` (this attempt definitely not accepted). Timeout, connection reset or `5xx` → `WAITING_RETRY`, and the message is **possibly accepted**. A permanent error caused by the message itself → this attempt definitely failed. A configuration fault (`401`, `403`, unverified domain, suspended account) → the message keeps waiting while **all sending is paused and an alert is raised** until an operator clears the pause; no message fails because of a configuration fault. **(c) `possibly_accepted` is sticky:** once any attempt of any generation may have been accepted, it stays true for the logical message, and a later definite or permanent failure never erases it. **(d) Settling:** the message becomes `FAILED` only while `possibly_accepted` is false, after a permanent error caused by the message, or when the retry horizon, link expiry or Start is reached. Otherwise it settles as **`UNCONFIRMED`** ("delivery outcome unknown"). In particular, a permanent error from a later attempt, after an earlier attempt may have been accepted, ends in `UNCONFIRMED`, not `FAILED`. **(e)** A failed freshness check settles a pending message as `DROPPED` if `possibly_accepted` is false, and as `UNCONFIRMED` with reason **obsolete** if it is true. The same rule applies when a pending message is settled because its event was deleted. `DROPPED` always means the message was definitely not submitted to the provider. **(f)** Any matched provider event moves `AWAITING_EVIDENCE` or `UNCONFIRMED` to `ACCEPTED` (NFR-REL-15). **(g) Contradicting evidence:** a verified provider event matched to a `DROPPED` or `FAILED` message is persisted and correlated like any other. The historical send state is **kept**, an anomaly is recorded on the message, and operators are alerted (NFR-OPS-1). The provider-reported facts are derived as usual (NFR-REL-18) and shown in owner-facing reporting (NFR-REL-11); such a message is never shown as definitely unsent. **(h) Bounded claim failures:** before each claim attempt, a durable counter is incremented in a separate short transaction that holds no event lock. A message whose claim transaction repeatedly fails to commit (for example because the worker crashes during it) is therefore retried only up to a configured bound. When the bound is reached it settles as `FAILED` if `possibly_accepted` is false, and as `UNCONFIRMED` otherwise. | R56, R59 |
| NFR-REL-14 | **Shared sending budget and reserved concurrency.** **(a)** All workers take a **send permit** from one PostgreSQL row before claiming a message. The row holds two token buckets: **priority** (authentication messages, NFR-REL-12) with guaranteed rate `rate_p` and burst `burst_p`, and **bulk** (all other messages) with guaranteed rate `rate_b` and burst `burst_b`. `rate_p + rate_b` equals the configured budget (confirmed provider quota × safety factor). **(b)** Priority never takes bulk permits, so a flood of authentication messages can't reduce bulk throughput. Refill that would overflow a full priority bucket **spills into the bulk bucket**, so idle priority capacity isn't wasted. **(c)** Permits are taken by a database function in its **own short transaction, holding no other lock** (NFR-CON-6). It locks the row, then reads `clock_timestamp()` **after** the lock is held, and never lets time move backwards relative to the stored `updated_at`, so lock waits can't produce negative elapsed time. **(d)** A worker without a permit sleeps for the computed deficit, with jitter. A permit taken when no message is claimable is returned. A permit lost to a crash only under-uses the budget and can never cause an overrun. Retries take new permits. **(e) Fairness:** within each class, claims are oldest-due first. A large fan-out can delay other bulk messages by up to its own duration; priority messages are unaffected. **(f) Provider `429`:** the message retries after a short delay. `rate_b` is halved (never below its minimum) and its tokens reset. `rate_p` is reduced only if `429`s persist with `rate_b` at its minimum. Rates recover additively to their configured values. A provider `Retry-After`, if sent, pauses both classes until that time. Configuration faults pause both classes (NFR-REL-13). **(g) Reserved concurrency (kept from R55):** every worker reserves at least one concurrency slot that only priority messages may use. The slot and the priority budget are independent and both required: bulk work can never occupy the slot, and bulk demand can never consume priority permits, so the priority lane isn't blocked by a large fan-out. **(h)** No Redis or other stateful component is introduced (R51). | R56, R55 |
| NFR-REL-15 | **Webhook ingestion and immutable event history.** **(a)** Signatures are verified on the raw body (`svix-id`, `svix-timestamp`, `svix-signature`), and invalid ones are rejected. **(b)** Each verified webhook is appended to an **immutable provider-event log**, never updated, with retention under OQ-5. Each entry holds its `svix-id`, the matched message and generation (or none), provider email ID, event type, provider timestamp, receipt time and minimal masked fields, and no tokens. **(c) Deduplication only on `svix-id`** (unique): a redelivered webhook is acknowledged and changes nothing. No other uniqueness rule may discard an event, so two legitimate events sharing provider ID, type and timestamp are both kept. Possible duplicates under different `svix-id`s are kept too; the outcome rules (NFR-REL-18) are unaffected by repeated facts. **(d) Matching:** by the `outbox_id` tag and generation tag, then by provider email ID. Unmatched events stay unmatched, are logged in masked form (NFR-REL-10), and are re-matched when a provider ID becomes known later. **(e)** A webhook that arrives before the worker records its API result applies its evidence immediately. The later result write is added to the attempt log and can't move the state backwards. The lease reaper ignores messages that are no longer `SENDING`. **(f)** A webhook is acknowledged only after its transaction commits (ENG-ERR-5). If the provider disables the endpoint, an alert is raised and missed events are replayed. | R56 |
| NFR-REL-16 | **Provider key generations and regeneration classes.** The provider idempotency key is the logical idempotency key plus a generation (`…:g1`); every retry within a generation reuses it. Each message type in §4.9 belongs to exactly one class. **Class A** (recoverable by an explicit user action: sign-in, re-authentication, email-change confirmation, registration verification, existing-registration access, ticket resend, management link replaced, staff invitation): **never regenerated**; recovery is the user's or owner's own action. **Class B** (important unsolicited notices: promotion, event change, event cancellation, ticket confirmation, registration-cancellation confirmation, waiting-list removal notice, email-change notice): **at most one regeneration**, and only if all of these hold: (1) the message is `AWAITING_EVIDENCE` with no evidence for window **W**; (2) webhook ingestion is healthy; (3) every send-time freshness check passes again (otherwise it settles under NFR-REL-13 e: `DROPPED` if `possibly_accepted` is false, `UNCONFIRMED` (obsolete) if it is true; a message waiting for evidence is always possibly accepted); (4) the retry horizon hasn't passed; (5) it is still on generation 1. **Class C** (reminder, waiting-list confirmation, waiting-list closed): **never regenerated**. A regeneration is the only remaining path to a duplicate physical delivery, apart from provider misbehavior, and it is logged. Tokens issued for attempts the provider refused are never delivered, and stay valid only until expiry, rotation or the end of the registration (FR-LNK-2/3). Single-use requests and invitations are still used up by their first confirmation. | R56 |
| NFR-REL-17 | **Deterministic rendering.** For the same message and the same current event data, rendering produces identical bytes apart from link tokens: no send timestamps or random values in the body. An identical retry therefore receives the provider's idempotent replay as confirmation. | R56 |
| NFR-REL-18 | **Delivery outcome from recorded facts.** The provider outcome is derived per generation from the provider-event log, never from arrival order, as separate facts. **Acceptance:** a `200`, a replay or any matched event. **Delivery:** `delivered_at`; a complaint also implies delivery. **Permanent failure:** `bounced_at`, `failed_at` or `suppressed_at`, with the reason. **Temporary delay:** `last_delayed_at`, informational only. **Complaint:** `complained_at`, with consequences under OQ-20. **Bounce semantics follow the provider's documentation:** for Resend, `email.bounced` is a permanent rejection and temporary problems arrive as `email.delivery_delayed`. An event whose payload marks a bounce as temporary is treated as a delay, never as a permanent failure (contract-tested, §12.1a). **Rules:** delivered only → Delivered. Permanent failure only → Failed (with reason). Both, with the failure's provider timestamp later → **"Delivered, later bounced"**: both facts are kept and it is reported as a failure. Failure earlier, or equal or missing timestamps → Delivered, with an anomaly logged. A delay never overrides an outcome. A complaint changes only its own fact. Open and click events are ignored (NFR-SEC-9). At message level, the message counts as delivered if any generation was delivered, and a duplicate is flagged if two or more generations were accepted. ## 10. Recommended technical approach (non-binding, A)

This section records the analyst's recommendation for keeping the system simple. It is not a requirement. **Superseded in part by R51** (approved stack and architecture constraints). §10 remains non-binding where R51 is silent.

- **One transactional relational database** with row-level locks, partial (filtered) unique indexes, and a way to claim queue rows without blocking (skip-locked style). Together these cover seat assignment, uniqueness and job claiming **without a separate message broker**. The database product is PostgreSQL (R51).
- **One web application plus one background worker** process, sharing the database. The worker polls the outbox and due scheduled items.
- **Event-row lock** as the single serialization point for all seat-affecting operations on an event (NFR-CON-1).
- **Reminder slot table** with a unique key on (registration, schedule version). Written in the same transaction as whichever message fills it (FR-NTF-1).
- **Staleness check at send time:** the worker locks the event row, rechecks status, schedule version and registration state, and marks the message `SENDING` in one transaction before calling the provider.
- **Link-token table** holding token hash, type (management/share), registration, issued time and revoked time. Lookup by hash. Rotation revokes all valid rows of one type and inserts one row, in one transaction (FR-ROT-3). The hash function and token library are not chosen.
- **Real-time count:** Server-Sent Events or short polling. WebSockets aren't needed for a one-way counter.
- **Email provider** must support webhooks for delivery and bounce events and, ideally, idempotency keys.

### 12.1 Email provider capability requirements (OQ-3)
Provisionally **Resend** (R56), subject to the production gates in §12.1a. The provider must provide:
1. A sending API that returns a **provider message ID** on acceptance, for correlation with webhooks.
2. **Idempotent submission**, either an idempotency key or deduplication on a client-supplied ID, to reduce duplicate deliveries after crashes (NFR-REL-3).
3. **Clearly distinguishable temporary and permanent errors** in API responses, so retry vs. fail decisions are correct (NFR-REL-4).
4. **Webhooks** for at least: delivered, hard bounce, soft bounce or deferral, dropped or suppressed, and spam complaint. Each must include the provider message ID and a reason.
5. **Signed or otherwise verifiable webhooks** and retried webhook delivery (NFR-REL-6, EC-25).
6. Visibility of the provider-side **suppression list**, so a suppressed address shows up as a permanent failure, not silent loss.
7. Sending limits that cover the burst of emails when a 10,000-person event is rescheduled or cancelled (NFR-PERF-1).
8. Support for the domain authentication standards SPF, DKIM and DMARC.
9. Acceptable data-processing terms and data residency (linked to OQ-5).
10. **Client-supplied message metadata**, where supported by the provider's API: each message carries metadata we supply (our logical outbox message ID), and the provider returns it in webhook events. This lets webhook events be matched to the logical message even after an ambiguous timeout, when the provider's message ID was never recorded. Metadata **does not replace** provider idempotency (item 2) and **cannot by itself prevent duplicate delivery** (NFR-REL-3). OQ-3 stays open (R52).
11. **Latency and availability suited to time-critical sign-in emails** (NFR-REL-12, R55).
12. **Idempotency-key retention longer than the retry horizon** (checked at startup, AC-162).
13. **Click and open tracking can be disabled** for every message (NFR-SEC-9).
14. **Configuration faults distinguishable from message-level failures** (NFR-REL-13).

### 12.1a Provider production gates and contract tests (R56)
Resend is used provisionally. **Production use requires:** (1) the contract tests below passing (AC-164); (2) a confirmed sending quota sufficient for NFR-REL-7 (OQ-18, AC-169); (3) a data-residency decision (OQ-19); (4) the other production blockers (OQ-5, OQ-9, OQ-14, OQ-17, hosting).

**Documented Resend behavior relied on** (Resend documentation, checked 2026-10-11): `Idempotency-Key` header, keys kept for 24 hours; an identical retry returns the original response without sending again; a different payload with the same key fails with `409 invalid_idempotent_request`; a duplicate request while the first is in flight fails with `409 concurrent_idempotent_requests`; `tags` on sends; Svix-signed webhooks with automatic retries (about 27.5 hours by calculation from the published schedule) and replay; event types `sent`, `delivered`, `delivery_delayed`, `bounced` (permanent), `complained`, `failed`, `suppressed`; default rate limit 10 requests per second per team, raisable on request.

**Contract tests** (undocumented or unverified behavior, never treated as guaranteed):
1. Whether rejected requests (`429`, validation `4xx`, `5xx`) store the idempotency key.
2. That a key-reuse `409` never sends.
3. That `concurrent_idempotent_requests` is returned while the first request is in flight.
4. That send-time `tags` appear in every event type (sent, delivered, delivery_delayed, bounced, complained, failed, suppressed).
5. That `svix-id` is stable across the provider's webhook retries.
6. Whether webhooks arrive duplicated, out of order, or before the API response.
7. Svix timestamp tolerance.
8. Error names and codes for each class, and whether a `Retry-After` header is sent.
9. Whether a suppressed recipient produces an API error or only a `suppressed` event.
10. That click and open tracking are off by default and stay off.
11. That an identical replay returns a byte-identical response.
12. That `email.sent` is emitted for every accepted email.
13. That `bounced` covers only permanent bounces, and how temporary problems are reported.
14. Measured acceptance latency (indicative only, from a small sample) and the quota actually granted.

**Limits:** at most **50 real emails per run**, a dedicated test team or API key (never production), controlled recipients only. The quota is verified separately (account settings or written confirmation), **never by load-testing the real provider**. The 10,000-message load test uses the fake provider only (AC-169).

### 12.2 Organizer and staff authentication security requirements (OQ-4)
The method is **decided by R55** (passwordless email sign-in links, FR-ORG-1 to FR-ORG-8). These items remain requirements, implemented as noted (A — list for review):
1. The organizer's email is verified before any event can be created (FR-ORG-1).
2. If passwords are used: storage with a slow, salted, adaptive password-hashing function, a minimum strength policy, and checks against known-breached passwords. If passwordless links are used: single-use, short-lived, hash-only tokens issued under the same rules as FR-LNK-1 and FR-LNK-9. *(R55: passwords are not used; the passwordless rules apply, FR-ORG-3.)*
3. Protection against credential stuffing and brute force: rate limiting and progressive delays or lockout, with no account enumeration in login, sign-up or recovery responses. *(R55: credential stuffing doesn't apply; flooding of sign-in requests is covered by NFR-SEC-3 and §12.4 item 1; no enumeration, FR-ORG-3 a.)*
4. Secure session handling: cookies that are inaccessible to scripts, sent only over HTTPS and restricted to same-site requests; idle and absolute session expiry; server-side session revocation; new session ID after login. *(R55: FR-ORG-4.)*
5. Re-authentication for high-impact actions: event cancellation, event deletion, and changing the account email. *(R55: FR-ORG-5.)*
6. Account recovery that cannot bypass email verification. *(R55: FR-ORG-7; lost-mailbox recovery is OQ-17.)*
7. Support for multi-factor authentication. Whether it is required is part of OQ-4. *(R55: not required in the MVP; the design permits adding it, OQ-15.)*
8. Audit records for sign-in, failed sign-in bursts, password or email changes, and session revocation. *(R55: FR-ORG-8.)*
9. Check-in staff sessions are invitation-based, scoped to one event, revocable immediately (FR-STAFF-3) and expire with the check-in window (FR-STAFF-4). *(R55: FR-STAFF-2, FR-STAFF-6, FR-STAFF-7; multiple devices are OQ-16.)*

### 12.3 Data categories requiring a retention policy (OQ-5)
Periods are open. Each category needs a defined retention period and deletion method:
1. Registrations, including participant email addresses and `CANCELLED`/`EXPIRED` history (Q8).
2. Unverified (`PENDING_VERIFICATION`) registrations that were never confirmed.
3. Token hashes of all types (verification, management, share, staff invitation, sign-in, email change), session ID hashes, and revocation records.
4. Email outbox messages, delivery statuses, provider message IDs and webhook payloads (which may contain addresses and bounce reasons).
5. Check-in records and check-in-undo audit records.
6. Audit logs: rotations, waiting-list removals, capacity, schedule, cancellation and deletion actions, and staff access changes.
7. Organizer accounts and their events, including cancelled events, which are never deleted by the owner in the MVP (R39). Their retention period is part of OQ-5.
8. Check-in staff invitations and staff access records.
9. Rate-limiting data and IP addresses.
10. Application logs and monitoring data (emails masked, tokens never logged, NFR-SEC-4).
11. Backups, which must follow the same erasure commitments.

### 12.4 Abuse and resource-exhaustion scenarios for limits (OQ-9)
Limits are open. They must cover at least:
1. **Email bombing a third party** through repeated registrations, existing-access emails or verification resends to a victim's address (limits per target address, per event and per IP).
2. **Registration flooding** of one event with many addresses, causing outbox growth and provider reputation damage.
3. **Token and ticket-code guessing** against verification, management, share and check-in endpoints (FR-LNK-7, FR-CHK-9).
4. **Rotation and resend spam** from a leaked management link (FR-ROT-8, FR-SELF-4).
5. **Mass-email amplification** by an organizer: repeated reschedules or cancellations of a large event, each fanning out one email per participant. This needs limits on reschedules per event per period and a maximum capacity per event.
6. **Resource exhaustion** through very large capacities or many events per organizer (database size, dashboard and real-time load).
7. **Staff-invitation spam** to arbitrary addresses.
8. **Check-in endpoint abuse** from a compromised staff session.
9. **Webhook flooding** or replay against the provider webhook endpoint (signature check plus rate limiting).
10. **Organizer sign-up and sign-in abuse:** flooding of sign-in requests (see item 1) and mass account creation. Accounts exist only after a confirmed sign-in (FR-ORG-1, R55).

### 12.5 Optional event end time (OQ-1 recommendation, not decided)
Recommended draft requirement, **not adopted**: an event may have an optional end time, which must be after Start. It is shown to participants and on the share view. It **does not** change the check-in window (`Start − 2 h` to `Start + 12 h`), link expiry (FR-LNK-5), the cutoff or reminder timing. These rules stay explicit and independent. Any future change to them would be a separate decision.
