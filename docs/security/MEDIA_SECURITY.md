# Media Storage: Security and Reliability Review (K-719)

**Date:** 2026-10-13 (S-20, prompt 33). **Scope:** event photographs (K-712, K-713): intake, processing, storage, serving, lifecycle, failures. Decisions: [PD-92](../process/DECISION_LOG.md) (design), [PD-100](../process/DECISION_LOG.md) (this review).

## Malware scanning: assessment

**Threat model.** Organizers are vetted (registration, email confirmation, Super Admin approval) and their uploads are limited; the risk is an organizer account taken over, or a crafted file, aiming either at **our server** (a decoder vulnerability) or at **viewers** (a file that a browser or another program would interpret harmfully).

- **Viewers:** the original file is never stored or served. Viewers only ever receive WebP files that our server encoded from decoded pixels, with `nosniff` and a restrictive CSP. A polyglot, script, macro or embedded payload in the upload does not survive re-encoding. An antivirus scan would add nothing here.
- **Our server:** the risk is in **decoding** untrusted bytes (libvips and its JPEG, PNG and WebP libraries through `sharp`). Re-encoding does not remove that risk: it is where the risk is. Mitigations in place: the signature check before decoding, the pixel limit before decoding, `failOn: 'error'`, no animation, a size limit, a concurrency limit, `sharp` kept current (`pnpm audit` in every CI run). Antivirus engines detect known malware families; they are not designed to catch new decoder exploits, so scanning would add little against this risk.

**Recommendation.** Antivirus scanning is **not required** for this design (originals are never kept or served). The worthwhile production measures are, in order: (1) keep `sharp` and the operating system's image libraries updated (dependency audit already in CI; add an automated dependency update job); (2) run the web process with memory and CPU limits (container limits in the deployment template, K-720) so a decoder fault cannot take the host down; (3) if the stakeholder wants defence in depth, isolate decoding in a separate, unprivileged process or container with no network access. If scanning is nevertheless required (for example by policy), the deployable option is a ClamAV daemon container (`clamd`, about 1 to 1.5 GB of memory for its signatures, a signature-update job), called before decoding through its TCP interface; the failure behaviour must be **fail-closed** (no scan result, no upload) with a clear 503. It is not built.

## Residual risks

- A decoder vulnerability in libvips or its libraries before an update is available (mitigated, not eliminated).
- An orphan file between a crash and the next sweep (unreachable: serving requires its row).
- The local storage adapter has no redundancy: the media directory must be backed up with the database (K-721).
