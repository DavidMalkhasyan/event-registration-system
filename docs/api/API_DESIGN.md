## 5. Authorization model

1. **Route policy:**
   - organizer-only routes reject a staff-only caller with `403 forbidden` (AC-26);
   - a missing or invalid session gets `401 unauthenticated`, and the cookie is cleared;
   - link routes accept only the link token.
2. **Resource check:** another owner's event or another event's staff resources get `404 not_found`. No data is ever returned (AC-155, NFR-SEC-6).
3. **Re-check under the event lock** for event-scoped writes, through `authorize(tx)` (AC-156). The re-check happens after the lock, so a revocation that commits first always wins.
4. **Recent authentication:** without it, `401 reauthentication_required`. The flow is in ADR-010 §8.
5. **Anti-forgery:** every state-changing cookie-authenticated operation lists `csrfToken` in its security requirement. The script check (§12) verifies this.

## 6. Link-resolution API contract (ADR-011, FR-LNK-7 to FR-LNK-10)

**Order of checks on every link route** **[ARCH: ADR-017 §2.3]:**
1. **`Origin`**, on `POST` only. A mismatch gets `403 origin_check_failed` and reveals nothing about the token.
2. **Token resolution** by `SHA-256(domain = route type)`, a plain read (TX-X02). Every unusable case gets the **generic `404`**.
3. **Sign-in confirmation only:** the pre-session token (ADR-010 §4). Failure gets `403 csrf_failed`.
4. **Body validation**, only after the token is known to be valid: `400` or `422`.
5. **Action rate limits** (`resend_limit`, `rotation_limit`): `429` problem.
6. **The transaction.** Authority is re-validated after the event lock; if it is gone, the generic `404`.

**Fragment transport is preserved:**
- No path segment, query parameter or schema property carries a raw token, and no session ID ever appears in a body.
- Issued links are full URLs whose token sits in `#t=` (`IssuedLinkUrl` pattern).
- `HEAD` never sets a cookie.

**`HEAD` behavior:** each of the six resolution routes has an explicit `HEAD` operation. It returns the same status and headers as the `GET`, with no body and no state change. A failed lookup counts toward the failed-lookup limit, which is security bookkeeping (FR-LNK-9).

**Generic body** (identical bytes; `404` or `429`; no correlation ID):

```json
{"code":"invalid_link","message":"This link is not valid or has expired.","hint":"If you were trying to register, please start again from the event page."}
```

**Infrastructure and unexpected failures** get `503` or `500` with `SafeServerProblem`: code and correlation ID only, identical for every link type and token (API-D1). The failed-lookup counter **fails open**, so invalid tokens can't become distinguishable through `503`s (ADR-017 §2.3).

## 7. Endpoint-specific rules

### 7.1 Public registration and sign-in requests

`submitRegistration` and `requestSignInLink` always return `202 {"status":"check_your_email"}`:
- every path writes exactly one outbox row (TX-R01, TX-A01), so the response is uniform (NFR-SEC-2, AC-5, AC-146);
- a closed or cancelled event returns `409 registration_closed`, which reveals event state only, and that is public anyway;
- over the limit, every address gets the same `429`.

### 7.2 Verification

`confirmVerification` returns one of three results (FR-REG-5, FR-REG-11):
- `confirmed`, with the ticket code and new management and share links;
- `waitlisted`, with the position, `positionMayChange: true` and a management link;
- `already_confirmed`, a distinct result while the link is within its original window (BR-30).

The page shows the issued links with copy actions and the recovery guidance (FR-LNK-10 f).

### 7.3 Rotation

`rotateLink` requires `linkType`, `requestId` (from `crypto.randomUUID()`, API-D2) and `confirmed: true`. Outcomes:

| Outcome | Response |
|---|---|
| Rotated | `{result: rotated, newLink, replacementEmailQueued}` |
| (a) Same request ID with the revoked token, within 15 minutes of the rotation's decision time | `{result: already_replaced}` |
| (b) The same, after 15 minutes | Generic `404` |
| (c) Used request ID with a currently valid token | `409 request_already_processed`. The page generates a new ID **without reloading**. |
| Not available (for example a share rotation while waitlisted) | `409 rotation_not_available` |
| Transaction failed | `503 rotation_not_applied` (FR-ROT-6) |
| Over the limit | `429 rotation_limit` |

### 7.4 Deletion preview token (API-D4)

`getDeletionPreview` returns:
- `eligible`;
- `blockers`;
- `requiredNoticeIssues` (failed, unconfirmed, bounced or anomalous required notices, with labels);
- `previewToken` = `v1.<keyId>.<exp>.<mac>`. The MAC (`K_preview`, ADR-010 §7) covers the account ID, event ID, schedule version and expiry, plus a SHA-256 **snapshot hash** of the eligibility state: status, confirmed count, waitlisted count, pending required notices, and the sorted list of reported required-notice issues with their states and fact timestamps. The token is valid for 10 minutes.

`deleteEvent` requires `confirmed: true` and `previewToken`. Inside TX-E06, **after the event lock**, the snapshot hash is recomputed:
- MAC invalid, expired, issued for another account or event, or snapshot changed → `409 preview_invalid`, and nothing is deleted;
- eligibility now fails → `409 deletion_blocked {reasons}`, `409 notifications_pending` or `409 cancelled_event_not_deletable`.

The owner therefore always deletes exactly what the confirmation step showed (FR-EVT-10, FR-DSH-6). The token is stateless; no table is needed.

### 7.5 Event creation idempotency (API-D3)

- **Request:** `requestId` (client UUID) and the event fields.
- **Fingerprint:** SHA-256 of the canonical JSON of the validated, normalized payload, without `requestId`. Fields: title, description (absent is treated as null), localStart, timeZone, utcOffset, capacity.
- **Inside TX-E01:**

  ```sql
  INSERT … ON CONFLICT (owner_account_id, creation_request_id) DO NOTHING RETURNING …
  ```

  - inserted → `201`, and the tasks are created;
  - conflict → read the owner's existing event: same fingerprint → `200` with that event (no new tasks); different fingerprint → `409 request_id_reused`, and nothing is created.
- **Concurrent duplicates:** the second insert waits on the unique index until the first commits, then takes the replay path. Exactly one event is created.
- **Database:** D-17 (U-27, CK-70, TR-17), applied as R60.
- **Accepted limitation (EC-103):** the uniqueness record is stored on the event row, so idempotency **does not survive deletion**. After an eligible event is deleted, a late retry with the same ID creates a new event. There is no separate durable idempotency record. Clients retry only within a short timeout window. **[RISK]**

### 7.6 Rescheduling (API-D5)

- **Input:** `localStart`, optional `utcOffset` and `expectedScheduleVersion`. There is no `timeZone` field; the event's zone is preserved.
- **Version check:** a mismatch gets `409 schedule_version_mismatch {currentScheduleVersion}`.
- **Same start as now:** `200` with no change and no emails, so retries are safe.
- **Other errors:** `409 event_started`; `422` for past, nonexistent or ambiguous local times.

### 7.7 Check-in

- **Input:** `code` (normalized: upper case; the Crockford look-alikes `O`→`0`, `I`/`L`→`1`) and `requestId`.
- **Output:** `200 {outcome, firstCheckedInAt?}`. All seven outcomes are business results.
- **Failures:** a request ID reused by another principal gets `409 request_id_conflict` (D-5). Too many failed attempts get `429 check_in_failures` (FR-CHK-9).

### 7.8 Participant list and delivery labels (owner only)

The list is paged in registration order (K-723, PD-102): `?limit=` 1 to 1,000 (default 1,000) and `?cursor=` from the previous page's `nextCursor`, which is `null` on the last page. Waiting-list positions are counted over the whole event.

Each `emailIssue` has `messageType`, `sendState`, `label`, `providerOutcome?`, `reason?`, `at` and `anomaly`.

**Client retry policy** **[REC]:**
- Retry only network errors and `503`, with backoff and at most 3 attempts.
- Retry only on `request-id`, `state` or `absolute` operations.
- Never retry `4xx`, except one retry after `403 csrf_failed` (with a freshly fetched token) and after `429` once `Retry-After` has passed.

## 10. Server-sent events (API-D6)

- **Endpoint:** `GET /api/events/{eventId}/live`, for the owner or that event's staff.
- **Events:**
  - `count` `{checkedIn}`: sent first on connect, then after every committed check-in or undo (`NOTIFY`, coalesced for up to 250 ms; NFR-PERF-2 target 2 s at p95);
  - `access_ended` `{reason}`, sent just before the server closes the stream.
- **Housekeeping:** a `: keep-alive` comment every 15 s; `retry: 3000`; no `Last-Event-ID` replay, so every connection starts with the authoritative count (FR-DSH-3).
- **Authorization (API-D6, FR-STAFF-3):** each stream sends its updates one at a time. Before each send, the session is re-validated with a fresh database read; an idle stream is re-validated at least every 30 s. Ordinary requests keep their immediate checks.
  - **Guarantee:** no update is sent whose authorization check *began* after the revocation (or expiry) became visible. A stream closes at the first check that fails, so within 30 s plus one check.
  - **Accepted window:** an update whose check completed just before the revocation committed may still be written, at most one per stream. Closing this check-then-send race completely would need each send to be serialized with revocation, which a stream held by another process can't do cheaply. The window is accepted (AC-186, EC-104).
  - **Tests:** AC-186 forces three orders: revocation before the check, revocation between check and send, and an idle stream.
- **Limits:** at most 5 streams per session, plus a per-process cap; exceeding them gets `429`. The values are under OQ-9.
